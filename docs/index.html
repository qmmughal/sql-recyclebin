SQL Server never got Flashback Query.

    
Oracle DBAs have had it for two decades. SQL Server's options are a $2,000 log-reader tool, or a point-in-time restore that loses every transaction after the mistake unless you merge it back by hand.

    

      

        
THE RESTORE PROBLEM

        
Point-in-time restore is slow and lossy

        
Rolling back to before the accident means losing every legitimate change that happened after it, unless you stand up a second copy and merge manually.

      

      

        
THE TOOLING PROBLEM

        
Log-reader forensics tools are expensive

        
Commercial transaction-log readers can reconstruct what happened — for a licensing fee that's hard to justify until after the first incident.

      

      

        
THE COVERAGE PROBLEM

        
Express edition is usually left out

        
Most recovery tooling assumes Enterprise or Standard. SQL RecycleBin is a trigger + a JSON store — it runs on every edition since 2017.

      

    

  






  

    
How it works

    
Three commands. No agent, no separate service, no schema mirroring — changed rows are captured as JSON, so ALTER TABLE never breaks your safety net.

    

      

        
01

        
Enable capture, once

        
Generates a lightweight AFTER UPDATE/DELETE trigger on the table.

        EXEC rb.Enable @Table = 'dbo.Orders';
      

      

        
02

        
Someone makes the mistake

        
A DELETE without a WHERE. A mass UPDATE that zeroes a column. It happens — this is the moment the trigger was waiting for.

        DELETE dbo.Orders -- no WHERE
      

      

        
03

        
Look, then undo

        
See exactly what was lost as real typed columns, then reverse it — newest transaction first.

        EXEC rb.Deleted @Table = 'dbo.Orders';
EXEC rb.UndoLast @Table = 'dbo.Orders';
      

    

  






  

    
Honest limitations

    
This is a safety net, not a replacement for backups — and we'd rather you know the edges now than find them during an incident.

    

      
// v1 known limits

      
    
        
  • TRUNCATE TABLE, DROP TABLE, and minimally-logged bulk operations don't fire triggers — not captured.
    • 
        
  • Protected tables must have a primary key.
    • 
        
  • Updating a primary key value breaks before/after pairing for that row (the before-image is still captured).
    • 
        
  • Restoring is subject to your foreign keys — restore parents before children.
    •
